# Meeting 2026-05-12: API Notes Overload Matching Design

## Summary

- The meeting focused on how overload-specific API Notes should select declarations without breaking existing broad matching behavior
- The main design direction is to treat typed overload matching as an additive filtering layer over the current API Notes model
- The YAML syntax should clearly distinguish:
  - fields that select declarations
  - fields that apply changes to selected declarations
- Several questions remain open:
  - partial overload matches
  - omitted qualifiers
  - canonicalization
  - diagnostics
  - mixed C/C++ headers
  - future support for templates and aliases

## Decisions / Current Leaning

### Target upstream LLVM/Clang

- The work should primarily target upstream LLVM/Clang, not a Swift-only fork.
- API Notes have already been upstreamed into the main LLVM repository
- The Swift fork regularly mirrors or merges LLVM changes
- An upstreamable Clang design is therefore the right long-term target
- There are multiple LLVM-related forks in play, but the design should be aimed at the normal upstream API Notes implementation
- The practical question is which LLVM checkout/fork to use while developing, while still making the work upstreamable
- After investigation, the prototype appears portable across both trees
- The main difference found so far is a source-file naming/layout difference:
  - `Types.cpp`
  - `APINotesTypes.cpp`
- This difference does not appear to be a fundamental design difference

### Preserve existing broad matching

- Existing projects may rely on notes applying broadly to several declarations or overloads
- The design should avoid silently narrowing behavior when no typed filter is present
- Preferred compatibility model:
  - name-only notes keep existing behavior
  - typed constraints act as additive filters
  - the current matching system should be extended rather than replaced
  - a format-version bump may still be useful if the YAML syntax changes
- Important compatibility principle:
  - specify no filters and match everything, as today
  - specify filters and narrow the existing candidate set
- If several overloads match under existing behavior, notes may apply to all of them
- The initial leaning is not to change behavior that existing projects may already rely on

### Keep typed-vs-legacy out of the user model if possible

- The prototype currently uses a `keyKind` to distinguish:
  - legacy/name-only entries
  - typed entries
- useful for prototyping
- long-term source format should probably avoid exposing an explicit "legacy mode" vs "typed mode" split
- A cleaner model is to make selector semantics carry the distinction:

```c++
MethodSelector {
  parent context
  method name
  optional parameter constraints
  optional receiver constraint
}
```

- Notes without overload-specific constraints continue to behave like existing name-based notes
- Notes with constraints narrow the candidate set
- Backward compatibility should be additive rather than a reinvention of the model
- A useful implementation framing is:
  - start with the existing candidate set
  - reshape typed information as filters
  - filter existing candidates down
  - collapse this approach into something working incrementally

### Explicit typed filters should not fail silently

- Once a note provides signature or overload-specific information, a missing or ambiguous match should produce a useful diagnostic
- The exact diagnostic model still needs design work
- Diagnostic cases to consider:
  - candidate suggestions
  - typos
  - ambiguous namespace matches
  - type names from different namespaces
  - C vs C++ language-mode confusion
  - possible correction searches for misspelled type names

### Prefer small incremental implementation work

- The implementation should be split into small, reviewable PRs
- Design discussion and implementation details should be separated where possible
- Examples and corner cases should be collected as the design evolves
- Important workflow guidance:
  - use small individual PRs
  - keep changes incremental
  - make review easy
  - do not try to solve the whole design before the coding period
  - iterate at a steady pace during the coding period

## Proposed Design Shape

### Separate filters from actions

- Some API Notes fields select the declarations to which a note applies
- Other fields describe what should be applied to those declarations
- Reusing names such as `Type` for both matching and rewriting/annotation purposes can be confusing
- In one context, a `Type` field can mean a matching constraint
- In a different context, a `Type` field in API Notes can effectively overwrite or change the type of some properties
- It can also be understood as a way to change the type recorded by some API Notes / AST-facing annotations
- The `Type` field question should be considered across all relevant type-bearing API Notes contexts, not only one narrow parameter-matching case
- The core confusion is that one field name can both match types and change types depending on context
- That is a somewhat weird construct because the same field name can serve different purposes
- Examples:
  - `Name` behaves like a filter
  - `SwiftName` behaves like an action
  - some `Type` uses are effectively matching constraints
  - some `Type` uses are closer to changing the imported declaration
- Some fields imply actions such as appending information or adding an attribute/note to a declaration
- Other fields are only filters that decide which declaration or overload the action should apply to
- The YAML design should make this distinction explicit.
- Possible grouping keywords:
  - `Where`
  - `Matches`
  - `There`
  - another similar selector-only grouping
- The selector grouping should enumerate all constraints whose only purpose is to select the declarations to import or annotate
- The action side can probably stay mostly unchanged
- `SwiftName` could continue to mean the name to apply to the selected declarations
- This should make it clearer which fields imply an action and which fields only filter candidates

Possible shape:

```yaml
Where:
  Parameters:
    - Position: 1
      MatchesType: int
SwiftName: "..."
```

- The key user-facing idea should be clear:
  - first select declarations
  - then apply note fields to the selected declarations
- This could be a relatively small source-format change if existing action fields are preserved and only matching constraints are moved into a clearer grouping

### Consider a Swift-like `where` clause

- A `Where` clause may be a good analogy because Swift extensions use `where` to describe constraints
- Possible direction:
  - use `Where` for matching constraints
  - allow clauses for parameters, receiver qualifiers, or other selector fields
  - possibly allow a generic-like clause expression in the future
- Example idea:
  - under `Where`, say `Parameters`
  - for a parameter, specify `Position: 1`
  - then specify `MatchesType: integer` or similar
- The word `Parameters` may not be ideal if the section is really a constraint clause.
- A better name might be something closer to:
  - `Where`
  - `Constraints`
  - `Matches`
  - `There`
- The main goal is to distinguish filters from actions in the user model

### Use a selector/filter model

- The design direction is to view overload-specific notes as filters over a candidate set
- Candidate filtering model:
  - the declaration name selects an initial candidate set
  - optional parameter constraints narrow it
  - optional receiver constraints narrow it further
  - action fields are then applied to the remaining declarations
- This preserves the existing broad behavior while allowing overload-specific precision
- The only purpose of the typed selector information is to decide which declarations we want to import or annotate

### Receiver qualifiers may deserve explicit fields

- The prototype associates receiver-side information with `Position: -1`.
- This can represent the implicit object parameter
- It may be awkward long term for:
  - `const`
  - lvalue reference qualifiers
  - rvalue reference qualifiers
  - `volatile`
- Users may want to match on receiver type or receiver qualifiers without describing the receiver as a parameter again
- Making receiver qualifiers look like another parameter may make the design less uniform or less clear
- Part of the concern is composability
- Users may need to describe combinations such as:
  - lvalue-const overloads
  - rvalue-const overloads
  - no ref qualifier
  - explicit `&`
  - explicit `&&`
  - unusual `volatile` cases
- A special parameter position may make those combinations harder to explain.
- There is also a modeling question:
  - no ref qualifier may not correspond to a pointer type
  - a ref qualifier may be modeled as a pointer-like type internally
  - the user-facing syntax should still be clear
- The design should make sure all meaningful combinations can be covered
- Ordering should not make valid combinations hard to express

An explicit representation may be clearer:

```yaml
MethodQualifiers:
  Const: true
  RefQualifier: "&&"
```

- This remains an open design point
- Explicit selector fields may be easier to explain than a special parameter position

### Design the YAML with future templates in mind

- Template instantiations and generic-like matching are likely out of scope for the first implementation
- The YAML format should not block future support
- This matters especially for:
  - aliases
  - template arguments
  - richer type matching
  - generic-like constraints
- Type aliases are stringly typed in the prototype direction and would not work well under simple textual matching
- Template cases are challenging
- It is perfectly fine not to address template instantiations immediately
- The design should still leave room to support them later
- First priority:
  - make a good YAML design
  - make sure it can be implemented incrementally

## Matching Semantics

### Type equivalence level is not settled

- The prototype currently uses normalized type spelling rather than full semantic type equivalence
- Stronger canonicalization quickly expands the scope
- It affects:
  - readability
  - predictability
  - implementation complexity
  - diagnostics
- The design should deliberately choose a point on a spectrum:
  - verbatim textual matching
  - whitespace-tolerant matching
  - modifier-order normalization
  - AST-level equivalence
  - full semantic equivalence including aliases
- A useful way to think about this is as a knob:
  - on one end, the filter must look almost exactly like the source code
  - in the middle, whitespace or simple spelling differences may be tolerated
  - on the other end, syntactically different spellings that produce the same AST may match
  - the full-blast version includes type aliases and deeper semantic equivalence
- The chosen point on this spectrum needs a strong justification
- The design needs to justify why this specific matching boundary was chosen
- Questions to answer:
  - How similar should the filter look to the actual source code?
  - Should API Notes survive ordinary formatter changes?
  - Should order differences be canonicalized?
  - What happens when matching fails?
  - What diagnostics should users get?

Examples that stress this choice:

- whitespace differences
- reordered modifiers
- formatter interactions
- aliases
- namespace qualification
- `const int *` vs `int const *`
- lvalue and rvalue reference qualifiers
- `const` and `volatile` combinations

- Full alias-aware equivalence is likely out of scope for the first version
- The design should leave room for it later

### Type spelling and qualifier order are hard

- Some equivalent C/C++ type spellings may appear in different orders
- Example:
  - `int const *`
  - `const int *`
- These both describe a pointer to constant integer
- There may not be a perfect answer for all such cases
- The design should come up with a solution for the most important problems first
- Questions:
  - Do we require a certain order from users?
  - Do we canonicalize these strings somehow?
  - How far should canonicalization go?
  - How do we handle `volatile`?
  - How do we handle combinations of `const`, `volatile`, `&`, and `&&`?
- The solution should cover realistic scenarios without making the implementation unbounded

### Omitted qualifiers are a central compatibility issue

- Examples:
  - missing `const`
  - missing reference qualifiers
  - no ref qualifier vs `&` vs `&&`
  - omitted namespace qualification
  - omitted overload distinctions
- The unresolved semantic question is what omission means
- Possible interpretations:
  - match everything compatible
  - match all overloads
  - match only exact forms
  - accept partially-qualified type names
  - require fully-qualified type names
- Existing projects rely on broad matching when no filter is present
- Omission should probably remain broad when no typed filter is present
- Once a user writes a typed filter, the semantics need to be precise enough to explain whether the filter is:
  - exact
  - partial
  - intentionally broad

### Multiple matching overloads need a clear rule

- Current behavior can apply notes to several declarations if several declarations match
- The overload-specific design has to decide what happens when a typed filter matches more than one overload
- This includes the question of conjunctive vs disjunctive matching:
  - do multiple constraints combine with "and" semantics?
  - can a note express "or" semantics?
  - if several partial filters overlap, how should the overlap be interpreted?
- Possible models:
  - a filter must match exactly one overload
  - a filter may match multiple overloads
  - if several overloads match, apply the attributes to all of them
  - matching several overloads after specifying a filter is a diagnostic
  - all overloads must satisfy the condition
  - some overloads may satisfy the condition
- The initial leaning is to preserve existing broad behavior and make typed filters additive
- Partial filters still need a better user model
- This is especially important when:
  - a filter specifies only a subset of parameters
  - that subset matches multiple overloads
  - that subset does not match all overloads
- Open design question:
  - is that fine?
  - should it be a user error?
  - should it require an exact match?
  - should it require exactly one match?
- The current rough feeling is that existing broad behavior should be preserved unless the user model clearly says otherwise
- The raw design question is whether matching should be "all of these constraints must match" or "some of these alternatives may match."
- If a user writes only a subset of parameter constraints, the design must define whether omitted constraints admit other forms such as `const`, rvalue qualifiers, or other overload distinctions

A concrete three-overload example makes the "matches some but not all overloads" case easier to reason about:

```c++
void f(int, int, float);
void f(float, int, float);
void f(float, float, int);
```

- If one note matches `param 1 is float`, it matches the second and third overloads.
- If another note matches `param 2 is int`, it matches the first and second overloads
- Both filters match the second overload
- The design needs to decide whether overlapping partial filters are:
  - valid
  - diagnostic-worthy
  - resolved by an ordering rule
  - resolved by a merge rule
- This three-overload example should be kept around for email discussion and future reference

## Diagnostics / Error Handling

- Diagnostics need more design work.
- Important cases include:
  - duplicate overloads
  - ambiguous matches
  - typos
  - unmatched filters
  - candidate suggestions
  - namespace ambiguity
  - type names from different namespaces
  - diagnostics for C vs C++ confusion
  - compatibility with existing notes
  - possible misspelling correction
- The rough direction is that explicit typed filters should be stricter than legacy name-only notes
- A note that asks for a specific signature should not quietly do nothing when that signature is missing or ambiguous
- Error messages should ideally help users understand possible matching candidates and give advice
- Diagnostics may need to show possible matches again after a failure.
- Diagnostics should consider whether a misspelled type name can be corrected or suggested

## Edge Cases To Investigate

### Headers usable from both C and C++

- The same header may be consumed in both C and C++ modes
- C has no overloads, while C++ does
- Overload-specific API Notes may have different implications depending on language mode
- Questions to resolve:
  - Should typed overload filters be accepted in C mode?
  - If a typed note names a type incorrectly in C mode, should that be diagnosed even though there is only one declaration?
  - Should matching rules adapt depending on the consumer language?
  - Should typo correction or candidate search behave differently for C and C++?
  - Should unmatched typed references in C produce warnings?
  - Are we okay if people specify types in API Notes for C APIs even though there is only one overload?
  - Do dual-use C/C++ headers change the desired behavior?
  - Do "double header" or shared consumer-format cases change the desired behavior?
  - Should some overloading-specific logic be ignored in C?

### Namespace qualification

- Type names may be ambiguous if the same spelling appears in multiple namespaces
- The design should decide whether users must write fully-qualified names
- The design should decide whether partially-qualified names are acceptable
- The design should decide whether ambiguous matches should be diagnosed
- Questions:
  - If a type exists in multiple namespaces, are unqualified names okay?
  - Should users be directed to always write fully-qualified names?
  - If the same API Notes spelling matches different type names in different namespaces, should that be diagnosed?
  - Is namespace ambiguity one of the questions diagnostics should help answer?
- There was no concrete advice or final answer yet
- This is something to keep thinking about

### Aliases and templates

- String-based matching does not handle type aliases or template instantiations well
- These can be future work
- The initial representation should not make them impossible to support later
- The design should support a path toward:
  - type aliases
  - template instantiations
  - template arguments
  - more semantic matching

### Formatting and canonicalization

- The matcher should be robust enough that ordinary formatting changes do not unnecessarily break API Notes
- The matcher should not be so permissive that behavior becomes surprising
- The chosen canonicalization level should be principled and documented
- Formatter question:
  - if a user runs a formatter over code, should that be able to mess up their API Notes?
- Failure question:
  - when type matching fails, what should users see?
  - should diagnostics show nearby candidates?
  - should diagnostics suggest more fully-qualified names?

## Legacy Support / Format Compatibility

- Legacy support needs a clear plan
- Questions:
  - If the YAML format version changes, do we need two ways to read API Notes?
  - Should a version bump distinguish old notes from notes using typed overload filters?
  - Is a typed-vs-legacy pass a good implementation idea?
  - Should there be a link to an existing compatibility discussion or design note?
  - How should old entries map into the new representation?
  - Can multiple legacy entries map into one new selector/action model, or vice versa?
- The feature should be additive rather than a reinvention of API Notes
- The design should get a good understanding of current behavior first
- Current behavior appears to match everything in some cases when no typed filter is present
- A possible implementation model:

  - build the existing declaration candidate set
  - interpret typed information as additional filters
  - filter down the existing candidates
  - preserve existing broad behavior when no typed filters are present
- The goal is to collapse this approach into something working without introducing a confusing user-visible split

## Important Overall Themes

### Balance simplicity vs expressiveness

- The system should remain understandable
- The design should avoid excessive complexity
- The design should still cover realistic use cases
- Some incremental improvements are important even if they do not solve every scenario immediately
- The design should aim to cover all important scenarios over time

### Preserve existing behavior where possible

- The design should avoid breaking existing projects
- The design should avoid changing overload semantics unexpectedly
- The design should avoid silently narrowing notes that currently apply broadly
- Existing broad matching behavior is important compatibility context

### Make the design principled

- The chosen behavior should be:
  - explainable
  - documented
  - consistent
  - justified
- This is especially important around:
  - matching
  - canonicalization
  - partial filters
  - omitted qualifiers
  - diagnostics
- The design needs a good justification for how much matching normalization it supports

### Focus on future extensibility

- Even unsolved cases should influence the current architecture
- Future-facing concerns include:
  - templates
  - generics
  - qualifiers
  - canonicalization
  - language interop
  - namespace qualification
  - aliases

### Keep the user model clear

- The design should make it easy to explain:
  - which fields select declarations
  - which fields apply actions
  - what omission means
  - when a match is exact, partial, ambiguous, or broad
  - when diagnostics should be emitted
- The user should be able to understand whether a field is filtering candidates or changing imported declarations
